## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.

## ai-chat-landing (Chat UI)

Next.js 16 + shadcn/ui (Base UI, luma preset) chat frontend for the Dify AgenticRAG chatflow, in `ai-chat-landing/`. Questions stream through `app/api/chat/route.ts`; the Dify API key lives in `.env.local` (git-ignored — never commit it).

Rules:
- Validate with `pnpm typecheck && pnpm lint` inside `ai-chat-landing/` — NEVER run `pnpm build` while `pnpm dev` is running in the same directory (they share `.next/`; a build mid-request silently kills in-flight streams).
- `pnpm test` in `ai-chat-landing/` runs vitest (pure-logic unit tests, e.g. `lib/deck-url.ts`, `lib/history/`, `lib/pdf-export/`).
- Chat UI feature surface: `app/api/conversations/` proxies Dify `/v1/conversations*` (history groups, resume, delete — specs 014/015); `lib/pdf-export/` backs the header ⬇ PDF export (spec 013; remote answer images are proxied same-origin via `ai-chat-landing/app/api/image-proxy/route.ts` so they survive the html2canvas CORS raster); `scripts/wide-layout.mjs` is the CDP layout acceptance script (wide column ≥1280px, `--smoke` for behavioral checks — spec 016); `lib/history/search.ts` + `search.test.ts` power the sidebar case-insensitive search (spec 018); below md the sidebar is an overlay drawer with backdrop/Escape/selection close paths (spec 019); every fresh load initializes a fresh "New chat" draft — no demo fixtures (spec 020); the empty state shows six feature cards in a 3-col desktop grid — body-click sends, label links new-tab to the card's help page in `public/example1–6.html` (spec 021); while an answer generates, the send button morphs into a Stop control that halts the backend generation via `app/api/chat/stop` and finalizes the turn honestly (partial text kept, session-only "Stopped" caption — spec 027); finished answers render their trailing follow-up question (the "Want me to…?" paragraph) as blue text with a 💡 (`lib/follow-up.ts`, 2026-10-28); the "Hermes File Agent" chatflow lane routes Windows file-task prompts to the sidecar's `hermes_file_task` MCP tool, which gates create/write/read/list operations inside an allowed root (default `C:\temp` via `/mnt/c/temp`), executes via the host Hermes gateway (`172.17.0.1:8642`, bearer key), and writes an append-only audit log (`~/.config/agentic-rag-mcp/hermes-mcp/audit.jsonl`) — blocked/delete/out-of-root prompts are refused with reasons and never reach Hermes (spec 028); the "Hermes Local Agent" lane also routes program-launch prompts — any executable by name or full `.exe` path, never with arguments, never scripts/shortcuts, one target per request, ask-backs for no/ambiguous target — to the sidecar's `hermes_launch_app` MCP tool, which gates purely, executes via the same gateway, and audits every attempt as `operation=launch-app`; `ok` requires the agent's `LAUNCH: SUCCESS` attestation, and WSL interop must be enabled on the host for launches to actually start (spec 029); the lane also routes Office-control prompts — write cells, edit documents, create slides, compose emails — to the sidecar's `hermes_office_task` MCP tool, which gates tasks (save/read at any named location, any drive — unnamed saves default to `C:\OfficeMCP`; literal content only; recipient rules; overwrites only of user-named files with honest "replaced" reports and unsaved-changes ask-backs; OS permission errors relayed, never a fabricated success), keeps conversation state (active document + pending draft), and executes through the gateway's native MCP connection to the Windows-side Office automation service; email composes and sends only after a chat confirmation of the exact draft shown, and every step is audited as `operation=office-task` (spec 030; spec 031 removed the save-location boundary); the Hermes Local Agent lane also runs read-only diagnostics — "show my current IP address", "what's running", "show my system locale", "show disk spaces" — via the sidecar's `hermes_run_command` MCP tool, whose gate maps natural language onto a fixed allowlist (ipconfig/systeminfo/tasklist/whoami/hostname bare; ping/nslookup/tracert with one strict-charset host; Get-Volume for disk space) enforced in `hermes_run_gate.py`, refuses everything else with the list shown, requires `conversation_id` in the schema (timed + cancellable), and audits as `operation=run-command` (spec 033); general PowerShell requests route to `hermes_run_powershell(task, conversation_id, draft, confirm)` — a TWO-PHASE tool: the draft call registers the exact drafted command (never-list-scanned via `hermes_powershell_gate.py`, stored conversation-scoped, echoed verbatim, audited with exact text — nothing executes), and only a plain-affirmative confirm call executes the STORED text (the confirm call carries no command text — what was confirmed is structurally what runs); the system-integrity never-list (volume format, diskpart, boot config, shadow-copy deletion, recovery, BitLocker state, disk wipes) refuses even with confirmation, one command per request, output bounded with truncation named, and a cancelled confirm clears the pending draft (spec 034, `specs/034-powershell-execution/` incl. test-plan.md); the agent executes Windows commands via `mcp__WindowsMCP__PowerShell` (never its WSL terminal), retries `USER_CONTROL` consent waits, and falls back to the direct WindowsMCP SSE channel (127.0.0.1:8800) on gateway arg-strips; operational Hermes-lane tasks run the skill loop first (spec 036): `skill_search` before any action on the fleet (questions/chat skip it), auto-reuse only when `reusable` is true (rate > 0.80 AND ≥ 3 successes, feedback-driven decay — no time expiry), `skill_get` fills `{{placeholders}}` with honest ask-backs and marks gated steps for live re-confirmation (the record never pre-confirms), `skill_save` validates at the boundary (snake_case names, per-step `expect`, `{{slot}}` templates — machine-specific literals rejected; tier-2 needs a tier-1 pre-check first), `skill_feedback` is append-only and escalates after two consecutive failures — skills are never deleted; every desktop/diagnostic turn carries a `TIMING:` profile (total, first-event latency, event count, top gaps) surfaced in tool results and audited (`duration_s`+`timing`, 2026-11-09); the relay is guarded by the ANTI-FABRICATION LAW plus a structural `honesty_check` code node between `hermes_agent` and the answer (claims-of-action without a tool call are replaced) and a dispatch-leak detector (a leaked `<invoke …hermes_…>` tag proves an undispatched call and is replaced), both in the DSL. CDP acceptance instruments live in `scripts/` (wide-layout.mjs, landing-check.mjs, welcome-cards.mjs, stop-button-check.mjs).
- The shadcn skill in `ai-chat-landing/.agents/skills/shadcn/` is CLI-managed (`pnpm dlx skills add shadcn/ui`); `skills-lock.json` tracks versions — do not hand-edit it.

## Deployment automation (spec 011)

`python -m agentic_rag_mcp.deploy {redeploy|chatflow|verify|cleanup|all}` (run with the project venv's python) rebuilds the sidecar, updates + publishes the Dify chatflow in place, and runs the headless verification battery. Console credentials and the chatflow API key live in `~/.config/agentic-rag-mcp/config.toml` `[dify]` (or `DIFY_*` env vars) — NEVER commit them; the CLI redacts secrets in all output. After changing tool counts or the chatflow DSL, `all` is the one-command path. Runbook: `DEPLOY.md` Step 10.
